## Context

### 问题背景
当前前端存在两个相互关联的架构缺陷：

**1. 线索数据双写不同步**
- `gameStore.case.clues` 与 `cluesStore.clues` 平行存在，前者只在初次 `setGameState` 时写入，之后永不更新
- 用户通过场景搜查/审讯提取添加的线索只流入 `cluesStore`，UI 展示也依赖 `cluesStore`
- `InvestigationPage.tsx:23`、`DeductionBoard.tsx:42`、`ScenePage.tsx:23` 使用 `gameState.gameId === gameId` 作为缓存短路，跳过重拉 API → 跨页面切换后用户新增线索不同步
- `InterrogationPage.tsx:130` 相反，useEffect 缺 `gameState` 依赖，导致每次 mount 都无条件拉取（而不是按需）

**2. localStorage 跨游戏污染**
- 所有 store 使用静态 persist `name`（`clues-store` / `deduction-store` / `interrogation-store` / `watson-chat-store`）
- `StartPage.handleStartGame` + `gameStore.resetGame()` 只清内存态，未清 localStorage，也未清 `interrogationStore`
- 结果：新游戏首次打开 InvestigationPage 仍能看到上一局的线索、推理链、审讯历史、华生对话

### 目标
1. 建立"**后端为真源、前端 store 为视图缓存**"的清晰边界
2. 所有会话级记录（线索 / 推理链 / 审讯消息 / 华生消息）以 `gameId` 为 localStorage 命名空间持久化 → 跨页面切换与页面刷新保留，新游戏时彻底清除
3. `gameStore.case.clues` 彻底移除，线索由 `cluesStore` 独占
4. 四个页面挂载逻辑统一收敛到 `useGameSessionSync(gameId)` Hook

### 架构核心
- **gameId-aware Zustand storage 适配器 `createGameScopedStorage(storeName)`**：localStorage key 格式 `game:${activeGameId}:${storeName}`
- **`useGameSessionSync(gameId)` Hook**：页面挂载唯一数据入口，比对 activeGameId → mismatch 则清内存 → 后端拉取 → rehydrate 新命名空间
- **`StoreManager.clearAllGameSessions(exceptGameId?)`**：扫描 localStorage，批量删除所有 `game:*` 前缀 key
- **新游戏序列**：`clearAllGameSessions() → resetAll() → createNewGame(API) → setGameState(新) → navigate`

## 关键设计细节

### §1 gameScopedStorage.ts

```typescript
// frontend/src/store/gameScopedStorage.ts
import type { StateStorage } from 'zustand/middleware'
import { useGameStore } from './gameStore'

console.debug('[gameScopedStorage.ts] 加载模块')

export const GAME_SCOPED_STORAGE_PREFIX = 'game:'

/**
 * 返回 Zustand 兼容的 StateStorage，
 * 实际 localStorage key 命名空间化为 `game:${activeGameId}:${storeName}`。
 * 无 activeGameId 时读写均 no-op，避免产生无主数据。
 */
export function createGameScopedStorage(storeName: string): StateStorage {
  const buildKey = (): string | null => {
    const gameId = useGameStore.getState().gameState?.gameId
    if (!gameId) return null
    return `${GAME_SCOPED_STORAGE_PREFIX}${gameId}:${storeName}`
  }

  return {
    getItem: (_key: string) => {
      const full = buildKey()
      if (!full) {
        console.debug(`[gameScopedStorage:${storeName}] getItem 跳过：无 activeGameId`)
        return null
      }
      return localStorage.getItem(full)
    },
    setItem: (_key: string, value: string) => {
      const full = buildKey()
      if (!full) {
        console.warn(`[gameScopedStorage:${storeName}] setItem 跳过：无 activeGameId`)
        return
      }
      localStorage.setItem(full, value)
    },
    removeItem: (_key: string) => {
      const full = buildKey()
      if (!full) return
      localStorage.removeItem(full)
    },
  }
}
```

**关键设计点**：
- `_key` 形参忽略（Zustand 会传入 persist.name 常量），由 adapter 自主构造 namespaced key
- `activeGameId` 从 gameStore 读，所以 gameStore 本身**不接入**此 adapter，保持静态 `localStorage`
- 无 activeGameId 时 no-op 而非抛错，避免 React 渲染早期崩溃

### §2 useGameSessionSync.ts

```typescript
// frontend/src/hooks/useGameSessionSync.ts
import { useEffect, useRef } from 'react'
import { gameApi } from '@/services/api'
import { useGameStore } from '@/store/gameStore'
import { StoreManager } from '@/store/storeManager'

console.debug('[useGameSessionSync.ts] 加载模块')

/**
 * 页面级数据同步 Hook。
 * - gameId 与 activeGameId 不一致：清内存 → 后端拉取 → rehydrate 新命名空间
 * - 一致：后台 revalidate（stale-while-revalidate）
 * - 同组件实例内同 gameId 不重复触发
 */
export function useGameSessionSync(gameId: string | undefined) {
  const setGameState = useGameStore((s) => s.setGameState)
  const setLoading = useGameStore((s) => s.setLoading)
  const setError = useGameStore((s) => s.setError)
  const currentGameId = useGameStore((s) => s.gameState?.gameId)
  const loadedRef = useRef<string | null>(null)

  useEffect(() => {
    if (!gameId) return
    if (loadedRef.current === gameId) return

    const needsFullReload = currentGameId !== gameId

    const run = async () => {
      try {
        setLoading(true)
        if (needsFullReload) {
          console.info('[useGameSessionSync] gameId 变更，执行全量同步', { from: currentGameId, to: gameId })
          StoreManager.clearInMemoryGameScopedStores()
          const state = await gameApi.getGameState(gameId)
          setGameState(state)
          await StoreManager.rehydrateGameScopedStores()
        } else {
          console.debug('[useGameSessionSync] revalidate', { gameId })
          const state = await gameApi.getGameState(gameId)
          setGameState(state)
        }
        loadedRef.current = gameId
      } catch (e: any) {
        console.error('[useGameSessionSync] 加载失败', e)
        setError(e?.message ?? '加载失败')
      } finally {
        setLoading(false)
      }
    }
    run()
  }, [gameId, currentGameId, setGameState, setLoading, setError])
}
```

**顺序关键**：
1. 先 `clearInMemoryGameScopedStores` 清空所有非 gameStore 的内存态
2. 再 `setGameState(新 state)` 更新 activeGameId（之后 adapter 才能指向正确命名空间）
3. 最后 `rehydrateGameScopedStores` 让各 store 从新命名空间读取持久化数据（可能为空 = 首次访问）

### §4 StoreManager 新增方法

```typescript
// frontend/src/store/storeManager.ts（新增片段）
import { GAME_SCOPED_STORAGE_PREFIX } from './gameScopedStorage'
import { useInterrogationStore } from './interrogationStore'

// ... class StoreManager 内 ...

/**
 * 删除所有 game:* 前缀的 localStorage 条目
 * @param exceptGameId 可选，保留该 gameId 的所有 key
 */
static clearAllGameSessions(exceptGameId?: string): void {
  const toDelete: string[] = []
  for (let i = 0; i < localStorage.length; i++) {
    const key = localStorage.key(i)
    if (!key?.startsWith(GAME_SCOPED_STORAGE_PREFIX)) continue
    if (exceptGameId && key.startsWith(`${GAME_SCOPED_STORAGE_PREFIX}${exceptGameId}:`)) continue
    toDelete.push(key)
  }
  toDelete.forEach((k) => localStorage.removeItem(k))
  console.info('[StoreManager] clearAllGameSessions', {
    removed: toDelete.length,
    except: exceptGameId,
  })
}

/**
 * 清空所有接入 gameScopedStorage 的内存态
 */
static clearInMemoryGameScopedStores(): void {
  console.info('[StoreManager] clearInMemoryGameScopedStores')
  useCluesStore.getState().resetClues()
  useDeductionStore.getState().resetDeduction()
  useInterrogationStore.getState().resetInterrogation()
  useWatsonChatStore.getState().clearMessages()
}

/**
 * 触发所有接入 gameScopedStorage 的 store 从当前 activeGameId 命名空间
 * 重新 hydrate（读取 localStorage 覆盖内存）
 */
static async rehydrateGameScopedStores(): Promise<void> {
  console.info('[StoreManager] rehydrateGameScopedStores')
  await Promise.all([
    (useCluesStore as any).persist?.rehydrate?.(),
    (useDeductionStore as any).persist?.rehydrate?.(),
    (useInterrogationStore as any).persist?.rehydrate?.(),
    (useWatsonChatStore as any).persist?.rehydrate?.(),
  ])
}
```

mergeClues: (incoming: Clue[]) => {
  if (!incoming || incoming.length === 0) return
  set((state) => {
    const existingIds = new Set(state.clues.map((c) => c.id))
    const toAdd = incoming.filter((c) => !existingIds.has(c.id))
    if (toAdd.length === 0) return state
    console.info('[cluesStore] 合并后端线索', { incoming: incoming.length, added: toAdd.length })
    return { clues: [...state.clues, ...toAdd] }
  })
},

## 风险与回滚

### 关键风险
1. **mergeClues 的"已有 id 跳过"策略**：若未来后端支持删除/更新线索，会阻塞后端变更。当前后端只追加，安全。后续如需，升级为"以 updated_at 决胜"或"后端为准"。
2. **gameScopedStorage 在 activeGameId 缺失时 no-op**：若组件在 gameStore 初始化之前触发 persist，写入会丢失。已加 console.warn；useGameSessionSync 的调用顺序（先 setGameState 后 rehydrate）保证正常路径无此问题。
3. **Task 4 Case 类型拆分影响面大**：tsc 是护航，Task 6 必须逐条修完后再提交。
4. **Zustand `persist.rehydrate()` API**：v4+ 稳定可用；Task 2 使用 `as any` 容错，避免不同版本 typing 差异引发 tsc 报错。

### 回滚策略
每个 Task 独立一个 commit，若某步出问题：
```bash
git revert <commit-hash>
```
- Phase A 任意 Task 失败：单独 revert，不影响其他 Phase（尚未被引用）
- Phase B 失败：回滚后类型恢复原状，业务逻辑不受影响
- Phase C 某 store 失败：该 store 单独回滚，其他 store 不受影响
- Phase D 某页面失败：该页面单独回滚，其他页面不受影响
- Phase E 失败：StartPage 回退原 handleStartGame
